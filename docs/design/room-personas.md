# 방별 페르소나 — 설계

## 배경

지금은 **페르소나 하나 = 봇 프로세스 하나**다. 여러 역할을 두려면 config 를 나누고 봇을 여러 개
띄운다. 실제 구성이 그렇다:

```
cube-brain-trainer/tools/claude-telegram-bot/
  config.json          → 개발자 봇 (그룹 -1004361964230)
  config.planner.json  → 기획자 봇 (그룹 -1003316591811)
  .claude-bot/
    state.json                 ← 개발자 봇 상태
    config.planner.state.json  ← 기획자 봇 상태
```

이 구조에서 역할끼리 말을 주고받을 수가 없다. 텔레그램 쪽 제약이 결정적이다:

> **봇은 다른 봇이 보낸 메시지를 받지 못한다.** Bot API 규칙이라 우회가 없다.
> ([room-relay.md](room-relay.md))

그래서 봇 사이 전달은 파일 인박스밖에 길이 없고, 그건 상대 프로세스의 생사·경로·수명을 전부
따로 다뤄야 하는 일이 된다. **프로세스를 하나로 합치면 그 문제가 통째로 사라진다** — 전달이
`handle()` 에 합성 메시지를 넣는 것으로 끝난다(`/tell` 이 이미 그렇게 한다).

**역할을 프로세스가 아니라 방(포럼 토픽·DM)으로 가를 수 있게 한다.** 그러면 봇을 하나로 합칠 수
있고, 합치면 방 사이 전달이 곧 역할 사이 전달이 된다.

## 강제하지 않는다 — 합치는 건 프로젝트마다의 선택이다

**"한 폴더에 봇 하나"는 규칙이 아니라 권장이다.** 코드는 이걸 강제하지 않고, 강제할 이유도 없다.
페르소나 기능은 봇 개수와 **직교한다** — "config 에 페르소나 목록, 방이 그중 하나를 가리킴"은 같은
폴더에 봇이 몇 개 돌든 그대로 성립한다.

합칠 때 얻는 것과 잃는 것은 이렇다.

| | 합친다 (한 봇 · 여러 페르소나 방) | 나눈다 (봇마다 페르소나 하나) |
|---|---|---|
| 역할 사이 전달 | `/tell` 로 바로 된다 | **불가능** — 봇은 봇의 말을 못 듣는다 |
| 텔레그램 정체성 | 하나. 이름·아바타도 하나 | 역할마다 따로 |
| 한 방에 두 역할 동시 | 불가 (방마다 하나) | 가능 |
| 프로세스·재시작 | 하나 | 역할 수만큼 |

나눠 두는 게 맞는 경우도 분명히 있다:

- **한 그룹 안에 두 정체성이 동시에 필요할 때.** 토큰이 달라야만 된다. 합치면 영영 못 한다.
- **점진 이행 중.** 합친 봇을 옛 봇들과 나란히 띄워 보고 옮기는 편이 안전하다.
- **`allowedChatId` 를 완전히 분리하고 싶을 때.**

그래서 이 문서가 코드에 요구하는 것은 "봇 하나"가 아니라 **아래의 파일 범위 규칙**이다. 그것만
지키면 두 구성 다 깨지지 않는다.

## 폴더 단위 파일을 봇·페르소나 단위로 가른다

**이건 봇을 합치든 안 합치든 어차피 해야 하는 일이고, 지금 이미 새고 있다.**

`state.json` 만 config 이름에서 파생돼 안 섞이는데(bot.mjs:83), 나머지 두 파일이 그 규칙을 안 따라갔다.
그래서 cube 의 기획자 봇과 개발자 봇은 **지금 이 순간 메모리와 인수인계 노트를 공유하고 있다.**

| 파일 | 지금 | 고친 뒤 |
|---|---|---|
| `state.json` | config 이름에서 파생 — 안 섞임 | 그대로 |
| `memory.md` (bot.mjs:88) | `BOT_DIR` 하나 — **두 봇이 공유** | config + 페르소나에서 파생 |
| `codex-handoff.md` (bot.mjs:90) | `BOT_DIR` 하나 — **서로 덮어씀** | 방별로 (아래 곁다리 절) |
| `local.lock` (bot.mjs:1020) | `BOT_DIR` 하나지만 `lock.room` 을 방 키로 비교 | 그대로 — 봇이 여럿이어도 안 겹침 |

파생 규칙은 `state.json` 과 같게 간다.

```
config.json         + 페르소나 없음 → memory.md                     (지금과 동일)
config.json         + dev           → memory.dev.md
config.planner.json + 페르소나 없음 → config.planner.memory.md      ← 경로가 바뀐다
config.planner.json + dev           → config.planner.memory.dev.md
```

봇이 여럿이어도, 페르소나가 여럿이어도, 둘 다여도 안 겹친다.

**"이주 불필요"는 기본 config 에만 참이다.** 셋째 줄이 그 반례다 — `config.planner.json` 처럼 이름이
붙은 봇은 지금 `memory.md` 를 읽고 있으므로, 경로가 바뀌는 순간 **규칙이 통째로 주입에서 빠진다.**
게다가 지금 cube 의 `memory.md` 에는 **두 봇의 규칙이 섞여 쌓여 있어서** 어느 줄이 누구 것인지
자동으로 가를 수 없다.

- 부팅 시 1회 rename 은 `migrateData()`(bot.mjs:95) 선례를 그대로 쓴다.
- **섞인 내용을 나누는 건 사람 손이 필요하다.** 이주 코드가 해줄 수 있는 건 복사뿐이므로, 양쪽에
  같은 내용을 두고 각자 지우게 하는 편이 안전하다 — 지운 규칙은 다시 쓰면 되지만 사라진 규칙은
  사라진 줄도 모른다.

## 결정

### 페르소나 목록은 config, 선택 결과는 방별 state

config 에 페르소나를 **목록**으로 둔다. 방은 그중 하나의 `id` 만 가리킨다.

```jsonc
{
  "projectDir": "/Users/me/clawd",   // 기존 키. 페르소나가 폴더를 안 정하면 이걸 쓴다.
  "persona": "…",                    // 기존 키. 페르소나를 안 쓰는 봇의 기본값으로 계속 산다.
  "personas": [
    { "id": "dev",     "name": "개발자", "prompt": "너는 이 프로젝트의 시니어 개발자다. …" },
    { "id": "planner", "name": "기획자", "prompt": "너는 프로덕트 기획자 겸 UX 담당이다. …",
      "model": "sonnet" },
    { "id": "scroll",  "name": "스크롤스티치", "prompt": "…",
      "dir": "projects/scroll-stitch",       // ← 작업 폴더. projectDir 기준 상대경로
      "permissionMode": "plan" }
  ]
}
```

- `id` — 방 state 와 세션 표에 적히는 키. 짧고 안 바뀌는 값.
- `name` — 사람에게 보이는 이름. 버튼·목록·`/status`·`/tell` 방 목록에 쓴다.
- `prompt` — 시스템 프롬프트에 주입할 본문. 기존 `cfg.persona` 자리에 들어간다.
- `model`·`provider` — **선택.** 페르소나를 고를 때 이 방의 기본값으로 적용한다. 기획은 sonnet,
  개발은 opus 처럼 쓴다. 방별 `model`·`provider` 는 이미 있으므로 값을 채워 넣기만 하면 된다.
- `dir` — **선택.** 이 페르소나의 작업 폴더. 아래 절 참고.
- `permissionMode` — **선택.** `dir` 을 쓰면 사실상 필수다. 아래 절 참고.

`personas` 가 없으면 지금과 완전히 같이 동작한다. **이 레포는 공개 배포물이고 대다수 사용자는
페르소나를 하나도 안 쓴다** — 그쪽 동작이 한 줄도 바뀌면 안 된다.

### 페르소나는 세션 경계에서만 정해진다

**대화 중에는 바꿀 수 없다.** 바꿀 수 있는 자리는 세션이 새로 시작하는 세 곳뿐이다.

| 자리 | 동작 |
|---|---|
| 처음 보는 방의 첫 대화 | 선택 버튼을 띄우되 **강제하지 않는다** |
| `/newchat` (새 토픽) | 새 방이므로 선택 버튼 |
| `/new` (세션 리셋) | 다시 고를 수 있다 |

이유는 셋이다.

1. 맥락이 쌓인 세션의 정체성이 도중에 바뀌면 **이미 쌓인 대화가 옛 페르소나의 것**이라 모순된다.
2. 고정이면 방별 메모리 분리(아래)가 안전해진다. 메모리가 방을 옮겨 다닐 일이 없다.
3. `/tell` 방 목록에 페르소나 이름을 걸 수 있다. 바뀔 수 있다면 전달이 도착했을 때 그 방이 이미
   다른 것이 돼 있을 수 있어서 이름을 못 건다.

**`/new` 를 예외로 둔 이유가 핵심이다.** "변경 금지"가 막으려는 건 *맥락이 이어지는 동안* 정체성이
바뀌는 것이고, `/new` 는 그 맥락을 버리는 자리라 취지에 어긋나지 않는다. 그리고 이 예외 하나가
막다른 골목 셋을 동시에 연다:

- **DM 은 방이 하나뿐이다.** `/newchat` 은 그룹 전용이라(`newTopicNotGroup`), 예외가 없으면
  DM 에서 한 번 잘못 고른 페르소나를 **영영 되돌릴 수 없다.**
- **기존 방은 페르소나가 없다.** "변경 금지"를 문자대로 적용하면 지금 돌고 있는 방들이 영원히
  기본값에 갇힌다. 미설정 → 설정은 변경이 아니므로 허용해야 한다.
- **고른 직후의 실수.** 아직 한 마디도 안 했으면 버릴 맥락이 없어 `/new` 가 무해하다.

### 첫 대화에서 선택을 강제하지 않는다

처음 보는 방에서 말을 걸면 선택 버튼을 띄우되, **안 고르면 기본 페르소나로 그냥 진행**한다.
폰에서 급히 물어봤는데 버튼부터 나오고 답이 안 오면 마찰이 크다. 나중에 `/new` 로 고르면 된다.

기본 페르소나 = `personas[0]`, `personas` 가 없으면 `cfg.persona`.

### `/sessions` 는 같은 페르소나 세션만 이어받는다

이건 새 제약이 아니라 **지금 새고 있는 자리를 막는 것**이다.

`/sessions`(bot.mjs:754~, `handleSessions` bot.mjs:2669)는 봇 상태가 아니라 **디스크의 jsonl 을
훑어서** 목록을 만들고, 기준이 **프로젝트 cwd** 다. 그래서 한 프로젝트의 **모든 방 세션이 한 목록에
섞여 나온다.** 지금도 개발방에서 열면 기획방 세션이 보이고, 고르면 그대로 이어진다.

페르소나를 도입하면 이게 위의 "세션 경계에서만" 규칙을 우회하는 **뒷문**이 된다. 기획 맥락이 쌓인
세션을 개발 페르소나 프롬프트로 이어받으면 정면 충돌이다. 그래서 이 규칙은 선택이 아니라
**앞 결정이 성립하기 위한 필수 조건**이다.

**jsonl 은 페르소나를 모르므로 봇이 따로 적는다.** 선례가 이미 있다 — `/name` 이 똑같은 일을 한다
(`state.sessionNames[sessionId] = 이름`, bot.mjs:937·2760).

```jsonc
// state.json
{
  "sessionNames":   { "<sessionId>": "톰" },          // 기존
  "sessionPersona": { "<sessionId>": "dev" }          // 추가
}
```

기록 지점은 **`setSid` 하나**다(bot.mjs:1242, 호출처 12곳). 여기서 방 페르소나를 같이 찍으면
compact 로 세션 ID 가 갈리는 경우까지 전부 덮인다 — 새 ID 를 만드는 자리가 전부 이 함수를 지난다.

### 페르소나를 모르는 옛 세션은 표시하되 경고한다

페르소나 도입 전에 만들어진 세션에는 기록이 없다. 두 안 중 **표시 + 경고**로 간다.

- **뺀다** — 안전하지만 **지금 이력이 통째로 사라진다.** 현재 방들은 전부 미상이라 `/sessions` 가
  빈 목록이 된다. 도입하자마자 기능이 죽는 셈이라 접었다.
- **표시 + 경고** ← 채택. 목록에 `페르소나 미상` 으로 남기고, 고를 때 한 번 알린다. 도입 이후
  만들어진 세션부터 자연히 정확해진다.

**덤:** 이 표가 생기면 `/sessions` 목록에 페르소나 이름을 **표시**할 수 있다. 지금은 미리보기 한 줄로만
세션을 구분하는데, 거르는 것보다 이 표시가 실사용에서 더 크게 느껴질 것이다.

### 페르소나는 작업 폴더를 가질 수 있다

`personas[].dir` 로 그 페르소나가 일할 폴더를 정한다. `cfg.projectDir` 기준 상대경로이고, 없으면
`cfg.projectDir` 을 그대로 쓴다 — **안 쓰면 지금과 동일하다.**

이게 있으면 한 봇이 여러 프로젝트를 맡을 수 있다. 실제로 지금 그 구성으로 봇이 나뉘어 있다:

```
clawd/config.json                           → /Users/jtchoi/clawd
clawd/projects/household-ledger/config.json → /Users/jtchoi/clawd/projects/household-ledger
```

**이 둘은 페르소나가 비어 있고 오직 작업 폴더만 다르다.** 즉 `dir` 은 역할이 다른 경우(cube)뿐
아니라 폴더만 다른 경우(clawd)까지 같은 틀로 흡수한다.

**가장 큰 이득은 `CLAUDE.md` 가 따라온다는 것이다.** Claude CLI 는 작업 폴더의 프로젝트 지침을
읽는다. 페르소나를 `projects/scroll-stitch/` 로 겨누면 그 폴더의 `CLAUDE.md` 가 자동으로 붙는다.
즉 **페르소나 = config 의 역할 프롬프트 + 그 폴더의 프로젝트 규칙** 으로 합성된다. 폴더마다 봇을
띄우는 지금 방식과 같은 값을 내면서 프로세스만 줄어든다.

**부수 효과: `/sessions` 가 절반 저절로 갈린다.** 세션 목록은 `resolve(cfg.projectDir)` 로
거른다(bot.mjs:829·838·909). 폴더가 다르면 세션이 자연히 나뉜다. `state.sessionPersona` 는 **같은
폴더를 공유하는** 페르소나 때문에 여전히 필요하지만, 폴더가 다른 쪽은 공짜로 해결된다.

#### 하위폴더로 제한하지 않는다

`DATA_DIR`(config 폴더)과 `projectDir` 은 지금도 서로 무관하게 논다. 기술적으로 막을 이유가 없다.
다만 **하위폴더를 권장한다** — `.ctb-outbox`·`.ctb-jobs` 가 각 작업 폴더 안에 생기므로, 흩어지면
프로젝트마다 `.gitignore` 를 따로 챙겨야 한다.

#### 권한도 페르소나별로 둔다 — `dir` 을 쓰면 사실상 필수다

`cfg.permissionMode` 는 지금 전역이다. 폴더를 가르는 순간 이게 위험해진다 — `acceptEdits` 하나로
**여러 저장소를 편집**하게 되는 셈이고, 잘못 고른 방 하나가 남의 프로젝트를 고친다. 되돌리기 어려운
쪽으로 실수가 난다.

`personas[].permissionMode` 를 두고, 없으면 `cfg.permissionMode` 로 떨어진다. 방별 `plan` 고정
(`/plan on`)은 이미 있으므로 좁히는 수단은 있지만, **기본값이 넓은 게 문제**라 여기서 좁힌다.

#### 비용 — `.ctb-outbox` 와 `.ctb-jobs`

이게 이 결정의 실제 작업량이다. 둘은 모듈 상수이고(bot.mjs:132·140) **`projectDir` 안에** 있다 —
codex 의 `workspace-write` 샌드박스가 쓸 수 있어야 해서 일부러 그렇게 뒀다(bot.mjs:130 주석).
폴더가 여럿이면 이것도 여럿이 된다.

된다. 그래서 별도 단계로 뺐다.

### 메모리는 페르소나별로 가른다

**이 설계에서 가장 조용히 망가지는 자리다.**

`memory.md` 는 `BOT_DIR` 하나에 있다(bot.mjs:88). 지금은 봇 = 페르소나라 문제가 없지만, 한 봇에
페르소나가 여럿이면 **기획 규칙이 개발 세션에 그대로 주입된다.** 게다가
`## RULES (must follow before anything else)` 로 시스템 프롬프트 최상단에 들어가서(bot.mjs:1869)
영향이 크다.

파일명을 config 이름과 페르소나에서 파생시킨다 — 규칙은 위 "폴더 단위 파일을 봇·페르소나 단위로
가른다" 절에 적었다. 페르소나를 안 쓰면 경로가 지금과 같으므로 **이주가 필요 없다.**

`loadMemory()` / `saveMemory()` 가 지금은 인자를 안 받는다. `chatId` 를 받아 방 페르소나로
경로를 고르게 고쳐야 하고, `/remember`·`/memory` 계열이 전부 이 경로를 탄다.

### `/tell` 은 유지하고 마커 경로만 고친다

`/tell` 은 이미 "같은 봇 안 방 사이 전달"이라 이 설계가 향하는 자리와 같다. 되돌리지 않는다.
페르소나가 붙으면 방 목록이 `봇유지보수 / 테스트` 대신 `개발자 · 개발방` 으로 좋아질 뿐 구조는
그대로다. 큐·홉 1·뮤트 확인·`_relay` 전파 같은 잔가지가 이미 다 붙어 있다.

다만 [room-relay.md](room-relay.md) 의 결정 하나를 **뒤집는다.**

> ~~에이전트는 `[[ctb-tell: 방 | 메시지]]` 로 **방까지 지정**하고, 받는 방에서 승인한다.~~
>
> **뒤집힌 이유:** 모델이 주소까지 정해버려서 사람은 "그 방에 보낼지" 만 고르게 된다. 실제로 원했던
> 것은 모델이 **문구만** 만들고 **주소는 사람이 정하는** 쪽이었다. 권한 면에서도 이쪽이 좁다 —
> 모델이 고를 수 있는 방의 집합 자체가 없어진다.

바뀐 형태는 이렇다. 마커에서 목적지를 빼고,

```
[[ctb-tell: 로그인 플로우 스펙 확정. 3단계로 줄였고 소셜은 뺐다.]]
```

**보내는 방에** 본문과 방 선택 버튼을 함께 띄운다.

```
📨 이 문구를 넘길까요?

로그인 플로우 스펙 확정. 3단계로 줄였고 소셜은 뺐다.

[ 개발자 · 개발방 ]  [ 기획자 · 리서치 ]
[ ❌ 안 보냄 ]
```

버튼 하나로 끝낸다. "전달할까요?" → "전달해줘" → 방 선택의 3단계도 검토했지만, 중간의 "전달해줘"가
**텍스트 답장이라 세션에 새 프롬프트로 들어가 턴이 한 번 더 돈다** — 토큰을 쓰고, 그 턴이 또 마커를
낼 수도 있다. `❌ 안 보냄` 버튼이 "전달 안 함"을 대신한다.

사람이 친 `/tell <방> <메시지>` 는 그대로 둔다. 사람이 이미 주소를 정한 경우다.

받는 방의 승인은 **없앤다.** 보내는 방에서 사람이 버튼을 눌렀으면 그게 승인이다 — `/tell` 과 같은
논리다. 승인이 두 번인 것은 같은 사람이 두 방을 다 보는 구성에서 군더더기다.

## 안 하기로 한 것

- **봇 사이 파일 인박스** — 봇을 합칠 수 있게 되면 대부분의 경우 필요가 없어진다.
  [room-relay.md](room-relay.md) 의 "다음 단계"는 이 문서로 대체한다. 봇을 일부러 나눠 두는 구성에서
  역할 사이 전달이 정말 필요해지면 그때 다시 연다 — **접은 게 아니라 미룬 것**이다.
- **한 방에 여러 페르소나** — 봇 하나 안에서는 텔레그램 계정이 하나라 발화자를 구분할 방법이
  이름표뿐이다. 프로토타입까지 갔다 접은 `/panel` 과 같은 자리이므로 다시 열지 않는다.
  (봇을 나눠 두면 지금도 되는 일이다 — 그쪽이 이 구성의 존재 이유다.)
- **페르소나별 명령 목록** — `BotCommandScopeChat` 으로 방마다 다른 `/` 자동완성을 줄 수는 있다.
  복잡도 대비 값이 낮다. 명령 집합은 전 페르소나 공통으로 둔다.
- ~~**페르소나별 `projectDir`**~~ — **하기로 바꿨다.** 처음엔 "한 봇은 한 프로젝트"로 잘랐는데,
  clawd 의 두 봇이 페르소나 없이 **폴더만 달라서** 나뉘어 있는 걸 보고 뒤집었다. 게다가 작업 폴더를
  가르면 그 폴더의 `CLAUDE.md` 가 따라오고 `/sessions` 도 저절로 갈린다. → 위 "페르소나는 작업
  폴더를 가질 수 있다".

## 구현 전에 막아야 할 구멍

적대적 리뷰에서 나온 것들. **전부 코드로 확인했다.** 순서는 심각한 것부터다.

### ~~`/new` 는 세션을 끝내지 않는다~~ — **0.4.13 에서 막았다**

이 설계의 핵심 불변식은 `/new` 가 맥락을 원자적으로 버린다는 가정 위에 서 있었는데, 코드는 그렇지
않았다. 페르소나와 무관하게 지금도 버그라서 **설계보다 먼저 고쳤다**(`commitSid`, 방 런타임의 `gen`).
남은 구멍들과 달리 여기는 구현이 이미 끝났으므로, 페르소나 작업은 이 전제를 믿고 시작하면 된다.

1. **돌고 있는 중에 `/new` 를 치면 옛 세션이 되살아난다.** `/new`(bot.mjs:3521)는 명령 구간이라
   busy 검사(bot.mjs:3644)보다 앞에서 처리된다. sid 를 지워도, 돌고 있던 자식이 끝나면서
   `setSid(chatId, res.sessionId)`(bot.mjs:3760)가 **옛 맥락의 후속 세션을 도로 등록한다.**
   결과: 새 페르소나를 골랐는데 다음 메시지가 옛 맥락 위에서 돈다. 게다가 `setSid` 가 기록 지점이라
   `sessionPersona[옛 맥락 세션] = 새 페르소나` 로 **오기록**까지 남는다.
2. **`/new` 는 현재 provider 세션만 지운다**(bot.mjs:3522 주석). Codex 세션은 살아남아, 다음 레이트리밋
   폴백이 **옛 페르소나 맥락의 Codex 세션을 이어받는다**(bot.mjs:3103~3106).

→ **고친 방식:** 방 런타임에 세대(`gen`)를 두고 `/new` 가 올린다. 실행은 시작할 때의 세대를 들고
있다가 끝날 때 다르면 결과 세션을 버린다(`commitSid`). 압축·계획 승인·Codex/Ollama 폴백처럼 세션
ID 를 새로 얻는 경로에 모두 걸었다. 그리고 `/new` 는 이제 **두 provider 세션을 다 지운다.**
답장 자체는 그대로 보낸다 — 실행 취소는 `/stop` 의 일이다.

### `state.sessionPersona` 는 턴마다 자란다 — `/name` 은 잘못된 선례다

Claude CLI 는 실행마다 새 세션 ID 를 만든다 — 코드가 그렇게 말한다(bot.mjs:3050 주석
"실행할 때마다 세션 ID 가 바뀌므로"). 즉 `setSid` 는 **매 턴** 새 키를 만든다. `sessionNames` 는 사람이
`/name` 을 칠 때만 늘어서 청소가 필요 없지만, 이쪽은 턴당 1항목 × 삭제 없음이다. 매 턴 `saveState`
하는 파일이 대화량에 비례해 영구 팽창한다.

→ 기록할 때 같은 방·같은 provider 의 직전 항목을 지운다. `/sessions` 는 디스크 최근 10개만 보므로
(bot.mjs:855·907) 그 이상 보관할 이유가 없다.

### 페르소나 `permissionMode` 가 안 지켜지는 경로가 셋이다

권한을 좁히려고 넣은 필드인데, 정작 넓어지는 자리를 안 지난다.

1. **계획 승인 실행**은 일부러 `permissionMode` 를 안 넘겨 `cfg.permissionMode` 로 돈다
   (bot.mjs:3198~3200 주석, 1856 `opts.permissionMode || cfg.permissionMode`). 페르소나가 좁은 값을
   가져도 승인 실행은 **cfg 의 넓은 값으로, 그 페르소나의 `dir` 에서** 돈다.
2. **Codex 폴백 가드가 `planLocked(chatId)` 만 본다**(bot.mjs:3095~3097). 페르소나의
   `permissionMode: "plan"` 은 안 본다. 그 방이 레이트리밋에 걸리면 Codex 가 `workspace-write` 로
   그 폴더를 **편집한다.** `/plan on` 을 만들 때 "권한이 조용히 넓어지는 유일한 자리"라고 막아 둔
   구멍을, 페르소나별 모드가 그대로 다시 연다.
3. **`cfg.codexSandbox` 자체가 전역이다**(bot.mjs:1989). 페르소나별 폴더를 도입하면 이것도 따라가야 한다.

### 예약 작업(cron)은 페르소나가 없다

`runScheduled` 는 `runPrimary(job.prompt, { sessionId: null, … })` 를 **`chatId` 없이** 부른다
(bot.mjs:2222). 지금은 `cfg.persona` 가 무조건 붙지만, 방 페르소나 조회로 바꾸면 이 경로엔 볼 방이 없다.

→ **cron 은 항상 기본 페르소나·`cfg.projectDir`·`cfg.permissionMode` 로 돈다.** 구현에서
`chatBucket(String(undefined))` 를 만들어 state 에 `"undefined"` 방이 생기지 않게 주의한다.

### 전달(`/tell`)은 누구의 페르소나로 도는가

`runRelay` 는 대상 방 키로 합성 메시지를 만들어 `handle()` 에 넣는다(bot.mjs:1680~1696). 페르소나·폴더·
권한은 **받는 방 것**을 따르는 게 맞다 — 지금도 큐·provider·plan 고정이 그렇다. 문서에 한 줄로 못박는다.

그리고 방 선택 버튼의 라벨(`개발자 · 개발방`)과 실제가 어긋날 수 있다. `pendingTells` 는 메모리에
무기한 남고 만료가 재시작뿐인데(bot.mjs:1723~1727), 그 사이 대상 방이 `/new` 로 페르소나를 갈 수 있다.
→ 버튼을 만들 때의 페르소나를 같이 저장하고, 실행 시점에 다르면 취소한다.

### 첫 대화 선택 버튼의 만료와 권한

"안 고르면 기본값으로 진행" 규칙 때문에, 첫 답이 나간 뒤 뒤늦게 버튼을 누르면 그건 **미드-세션 변경**이
된다. → **첫 턴이 시작되면 버튼은 만료**시키고 `/new` 로 유도한다.

또 `handleCallback` 은 방 화이트리스트만 검사하고 **누가 눌렀는지는 안 본다**(bot.mjs:3227~3230).
그룹에서 아무 구성원이나 방의 정체성을 정하게 둘지 정해야 한다.

### 살아 있는 Codex 세션은 옛 마커 문법을 계속 쓴다

Codex 는 세션을 만들 때만 `tellInstruction` 을 받는다(bot.mjs:1971~1981). 5단계 배포 후에도 이미
열려 있던 Codex 세션은 `[[ctb-tell: 방 | 메시지]]` 를 계속 낸다.
→ 파서는 **한동안 두 문법을 다 받는다.** 목적지가 있으면 그 방을 버튼 기본 선택으로 쓴다.

덤으로 확인된 기존 구멍: **Codex 폴백 경로는 페르소나를 아예 안 싣는다.** `runCodex` 의 주입이
`opts.injectMemory` 안에 있는데(bot.mjs:1971~1981) 폴백 호출부(bot.mjs:3103)가 그걸 안 넘긴다.

### 잔가지

- **`id` 는 파일명이 된다.** `[a-z0-9-]` 로 제한한다. `dev/x` 같은 값이 경로를 깨뜨린다.
- **`ctb` 도 `memory.md` 를 하드코딩한다**(ctb.mjs:314). 3단계만 먼저 하면 ctb 가 옛 경로를 읽어
  봇과 어긋난다. 구버전 `ctb` 가 설치된 채 봇만 올라간 경우도 같다.
- **미상 세션을 채택하면 현재 페르소나로 낙인찍힌다** — `setSid` 가 찍기 때문이다. 실제로는 다른
  페르소나의 맥락이어도 이후 영구히 그렇게 표시된다. 의도라면 의도라고 적어 둔다.

## 단계

| 단계 | 내용 |
|---|---|
| 1 | `cfg.personas[]` · 방별 `persona` · 주입 3곳 · `/persona`(현재 표시 + `/new` 안내) |
| 2 | 선택 버튼 3지점 (첫 대화 · `/newchat` · `/new`) |
| 3 | 메모리 페르소나별 분리 |
| 4 | `state.sessionPersona` + `/sessions` 필터·표시 |
| 5 | `/tell` 마커에서 목적지 제거 → 방 선택 버튼, 목록에 페르소나 이름 |
| 6 | `personas[].dir` + `permissionMode` — outbox·jobs·cwd·`ctb` 를 방별로 (제일 큰 덩어리) |
| 7 | cube·clawd 의 config 합치기 (**선택** · 이 레포 밖, 운용 작업) |

3 은 안 하면 조용히 망가지므로 4·5 보다 앞에 둔다. 4 는 2 가 없으면 채울 값이 없으므로 뒤에 둔다.
7 은 안 해도 1~6 이 전부 동작한다 — 합치면 역할 사이 전달까지 따라올 뿐이다.

**6(작업 폴더)은 1~3 과는 독립이지만 4 와는 아니다.** 역할 프롬프트 없이 폴더만 갈라도 값이
나오므로(clawd 가 그 경우다) 급하면 1~2 뒤에 바로 해도 된다. 다만 세션 목록 필터가 `cfg.projectDir`
하나를 기준으로 삼고 있어서(bot.mjs:829·838·909), **6 을 4 보다 먼저 하면 `dir` 을 가진 방에서
`/sessions` 가 "자기 세션은 하나도 안 보이고 남의 것만 보이는" 상태가 된다.** 순서를 바꾸려면 그
필터의 방별 파라미터화를 6 에 반드시 포함시켜야 한다.

덩어리가 제일 크고 `permissionMode` 를 같이 좁히지 않으면 한 설정으로 여러 저장소를 편집하게
되므로 **둘은 한 단계로 묶었다.**

**3 의 메모리 분리는 봇을 합치지 않아도 지금 당장 값이 있다.** cube 의 두 봇이 이미 메모리를
공유하고 있으므로, 1~2 없이 3 만 먼저 해도 실제 버그가 하나 사라진다.

## 열린 질문

- **`/status` 에 페르소나를 어떻게 보이나.** 방 설정이 이미 여럿이라(provider·model·plan 고정)
  줄이 늘어난다. 이름만 한 줄이 무난해 보인다.
- **페르소나 `prompt` 를 config 에 통째로 넣으면 config 가 커진다.** 파일 경로를 가리키게 할지
  (`"promptFile": "personas/dev.md"`) 나중에 판단한다. 처음엔 인라인으로 충분하다.
- **`dir` 이 가리키는 폴더가 없으면?** 부팅 때 만들지, 그 페르소나만 비활성으로 둘지. 남의
  프로젝트를 새로 만들어 버리는 쪽이 더 놀라우므로 후자가 유력하다.
- **`id` 를 바꾸면 `sessionPersona` 의 옛 값이 뜬다.** 미상과 같이 취급하면 되지만, config 를
  고칠 때 경고를 띄울지는 정하지 않았다.
