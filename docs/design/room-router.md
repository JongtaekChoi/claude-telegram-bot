# 잘못 보낸 방 — 접수처 방 (`/router`) — 설계

## 배경

포럼 그룹에서 **특정 토픽에 갈 말이 상위 방으로 나가는 사고**가 반복된다. 그룹을 열면 기본으로
상위에 서고, 알림에서 들어가도 그렇고, 답장하려다 토픽 밖으로 나오기도 한다. "조심하자"로는
안 고쳐지는 종류다 — 사람의 부주의가 아니라 텔레그램 포럼 UI 의 구조가 그렇다.

지금 이 레포의 방 구성이 그 사고 지점을 그대로 보여준다.

```
-1003573665054       봇유지보수          ← 상위. 여기가 사고 지점
-1003573665054:573   봇유지보수 / 구현
-1003573665054:520   봇유지보수 / 기획
-1003573665054:11    봇유지보수 / 테스트
-1003573665054:35    봇유지보수 / 플랜
```

상위 방도 다른 방과 **똑같이 세션을 가진 실행 방**이다. 그래서 잘못 쓰면 조용히 실행되고,
알아차렸을 때는 이미 (1) 엉뚱한 세션의 컨텍스트가 오염됐고 (2) 그 실행에 쓴 토큰과 시간이
버려졌고 (3) 정작 그 말이 가야 할 방은 그 말을 못 들었다. `/stop` 이 있지만 타이핑이 실행보다
느리다 — 알아차린 시점에는 대개 늦었다.

> 상위 토픽의 방 키가 그룹 ID 와 같다는 점은 이미 [room-personas.md](room-personas.md) 의
> "안 하기로 한 것"에 적혀 있다. 한 키에 "그룹"과 "상위 토픽" 두 의미가 겹친다.

## 결정

### 접수처 방은 실행하지 않는다 — 주소를 묻는다

프롬프트가 오면 provider 를 띄우지 않고 어디로 보낼지 버튼으로 묻는다.

```
어디로 보낼까요?
[구현] [기획] [테스트] [플랜]
[여기서 실행] [취소]
```

핵심은 편의가 아니라 **실수가 조용히 실행되는 경로 자체를 없애는 것**이다. 잘못 눌러도 잘못
보낸 게 아니라 안 보낸 게 된다. 실패가 시끄러워진다.

### ~~어느 방이 접수처인지는 방별 state 에 둔다~~ — **명령도 state 도 없앴다 (자동 판정)**

원래 안은 이랬다. `config.json` 에 방 키 맵(`rooms`)을 두는 안은
[room-personas.md](room-personas.md) 에서 이미 접었으니(토픽 `threadId` 를 사전에 알 수 없고
상위 토픽의 키가 그룹 ID 와 겹친다), 페르소나 선택이 그랬듯 **그 방에서 `/router on` 으로 켜고
결과는 state 에 적는다.**

> **뒤집힌 이유:** config 를 접은 논증은 "*config 가 아닌 다른 곳*이 필요하다"까지만 말했지
> "**사람이 켜야 한다**"까지 말하지 않았다. 봇은 `/router on` 이 알려주려던 것을 이미 안다.
>
> - `state.sessions[그룹ID].forum` — `chat.is_forum` 에서 자동으로 찍힌다(`rememberForum`)
> - 방 키가 그룹 ID 와 같은가 — 그게 곧 상위 토픽이다
> - 형제 토픽이 있는가 — `state.sessions` 키에서 바로 나온다
>
> 셋이 동시에 참인 방이 **사고가 나는 방과 정확히 일치한다.** 그래서 "안 하기로 한 것"의
> *모든 방에 기본으로 켜기* 가 걱정한 DM·단일 방 봇은 구조적으로 안 걸리고, 토픽을 안 쓰는
> 포럼도 형제가 없어 안 걸린다.
>
> 결정적인 건 **켜는 걸 사람에게 맡기면 "조심하자"로 되돌아간다**는 것이다. 재발 보고가 온
> 상황에서 `/router on` 을 치는 걸 잊으면 기능이 있어도 사고가 난다. 그리고 실패 방향이
> 비대칭이다 — 자동으로 켰다가 틀리면 **탭 한 번**, 안 켜서 놓치면 세션 오염 + 토큰 낭비 +
> 그 말이 목적지에 안 감. 오탐도 조용하지 않다(버튼이 뜬다).

그래서 **명령이 없다. state 필드도 없다.** `routerSiblings(chatId)` 가 위 셋을 그 자리에서
판정하고, 빈 배열이면 게이트가 아예 안 걸린다.

~~**되돌릴 길이 없는 것이 이 안의 유일한 대가다.**~~ 상위 방에서 자주 일하면 매번 탭이 하나 붙고
빠져나갈 방법이 `state.json` 손편집뿐이다 — `/allow` 로 방금 없앤 바로 그 문제다. **이 대가는
아래의 조용한 창으로 갚았다.** 그래도 남으면 그때 **끄는 용도로만** `/router off` 를 붙인다
(기본 동작은 자동으로 두고). 미리 붙이지 않는 건, 필요해지기 전에는 명령 하나 · state 필드
하나 · 안내 문구 여섯 자리가 순수한 비용이기 때문이다.

> **그 "그때"가 왔다 (0.7.0, 2026-10-01).** 상위 토픽에서 일부러 일하는 쪽이 실제 사용 패턴이었고,
> 조용한 창으로 갚은 것만으로는 모자랐다(게다가 창의 끝 스탬프가 코드에서 빠져 있어 체감은 더
> 나빴다 — 아래 참조). 예고한 그대로 **끄는 용도로만** 붙였다: 기본은 자동 판정이고 `/router off`
> 가 방별로 그 기본을 끈다. 값도 예고한 그대로 치렀다 — 명령 하나, `state.sessions[방].router`
> 하나, 안내 문구 여섯 자리.

### 대화가 이어지는 중이면 묻지 않는다 (`ROUTE_QUIET_MS`, 10분)

바로 위 대가를 실제로 치러 보고 추가했다. 상위 방에서 **일부러** 일을 시키는 사람은 한 마디마다
탭이 하나씩 붙는다. 그렇다고 끄는 스위치를 주면 끈 방은 보호가 통째로 사라진다 — 스위치는
성가심과 보호를 같이 버린다.

> **0.7.0 에서 스위치를 줬고, "보호가 통째로 사라진다"는 대목만 고쳤다.** 끈 방이 맨몸이 되는 건
> 맞아서, 버튼 대신 **에이전트에게** 시킨다: 시스템 프롬프트 한 줄로 "도구를 쓰기 전에 이 방
> 맥락에 속하는지 보고, 아니면 실행하지 말고 어느 토픽인지 되물어라"(`deskGuardInstruction`).
> 시스템 프롬프트는 턴 **시작**에 읽히므로 검사가 파일 수정보다 앞선다. 대신 강제가 아니라
> 지시이고, "테스트 돌려줘" 처럼 **어느 방에서나 말이 되는 요청**은 못 거른다 — 버튼을 끄기로
> 한 대가다. 켜 둔 방에는 안 붙인다(한 말에 두 번 걸린다).

그래서 **시각으로 가른다.** 이 방에서 마지막으로 실행한 지 `ROUTE_QUIET_MS` 안이면 묻지 않고
그냥 실행한다.

```
조용한 뒤의 첫 말   → 묻는다      (사고는 거의 다 여기다)
그 뒤 10분 안의 말  → 그냥 실행   (일부러 여기서 하는 대화)
```

새어나오는 사고는 **다른 토픽에서 한참 일하다 상위에 흘린 첫 메시지**라 정의상 조용한 뒤에
온다. 반대로 여기서 하는 대화는 첫 한 번만 버튼을 거치고 그 뒤로는 평소처럼 흐른다. 오탐과
정탐이 시간축에서 갈리는 것이지, 내용을 읽고 맞히는 게 아니다 — **내용으로 방을 추측하는 안은
아래 "안 하기로 한 것"에 그대로 남는다.** 모델을 한 번 더 돌리지 않고 `Date.now()` 만 본다.

기준점은 실행의 **시작과 끝 양쪽**에 찍는다. 20분짜리 작업이 끝나자마자 이어 말하면 "시작한 지
20분"이라 창 밖이 되는데, 그건 대화가 끊긴 게 아니다.

> **이 문단은 2026-10-01 까지 거짓이었다.** 끝 스탬프가 `runApprovedPlan` 의 `finally` 에만 있고
> `handle()` 의 `finally` 에는 빠져 있었다 — 문서와 코드 주석은 둘 다 양쪽에 찍는다고 적어 둔 채였다.
> 그래서 상위 토픽에서 10분 넘게 걸린 작업이 끝나면 이어지는 말에 **다시 물었다.** "상위 토픽에서
> 일할 때 성가시다"는 사용 보고의 큰 몫이 이 한 줄이었다. 설계가 틀린 게 아니라 코드가 설계를
> 따라가지 않았던 경우라, 문서를 고치지 않고 코드를 고쳤다.

시각은 방별 런타임(메모리)에만 둔다. 재시작하면 한 번 더 묻게 되는데 그 편이 맞다 — 재시작은
대화가 끊긴 자리다. state 스키마도 안 늘어난다.

**대가는 정직하게 말해, 이 창 안에 새어나온 말은 못 잡는다는 것이다.** 다만 그건 이 기능이
없던 때와 같은 실패지 더 나빠지는 건 아니고, 그 대신 이 기능이 상시로 쓸 만해진다. 10분은
"한 대화가 이어지는 시간"의 감으로 잡은 값이고, 설정으로 빼지 않았다 — 조절하고 싶어지기
전까지는 키 하나가 순수한 비용이다.

### 넘어간 메시지는 "전달"이 아니라 "고쳐 쓴 주소"다 — 머리말을 붙이지 않는다

`runRelay()` 는 이런 머리말을 붙인다(bot.mjs:1865).

```
[Relayed from: … — another room of this bot, passed on by the person using it]
Answer here, in this room. This is not the user typing to you directly…
```

여기서는 이게 **거짓말이다.** 사람이 자기 말의 주소만 고친 것이므로, 받는 방은 그 사람이 그
방에서 친 것과 완전히 같게 받아야 한다. 머리말도 `_relay` 표시도 붙이지 않는다. `/tell` 은
"옆방에서 알아낸 걸 넘기는" 것이고 이건 "처음부터 여기로 왔어야 할 말"이라, 같은 배관을 쓰되
의미는 다르다.

> **0.7.0 에서 절반만 뒤집었다.** 위 결정은 **모델이 받는 프롬프트**에 대한 것이고 그대로 유효하다
> — 머리말도 `_relay` 도 안 붙인다. 그런데 그 원칙을 **사람이 보는 화면**에까지 적용한 게 과했다:
> 넘어간 토픽에는 답만 떠서, 그 토픽만 보는 사람에게는 **질문 없는 답**이 됐다(원문은 상위 토픽에
> 남아 있다). 그래서 `runRoute` 가 `handle()` 앞에 안내를 한 장 보낸다 — `/tell` 의 `tellIncoming`,
> `ctb send` 의 `dispatchIncoming` 과 같은 자리이고, 둘 다 프롬프트와는 별개의 `send` 다.
> 문구는 `tellIncoming` 을 재사용하지 않는다(전달이 아니라 "주소를 고친 말"이다).
>
> 원문은 `routePreview` 를 길이만 늘려(300자) 쓴다 — 자르는 규칙이 둘이면 갈린다. 공백을 접으므로
> 붙여넣은 로그는 한 줄로 뭉개지는데, 안내의 목적이 원문 재현이 아니라 "무슨 말에 대한 답인지"라
> 그쪽을 택했다. **첨부는 실물이 안 간다** — 봇은 처리하지만 텔레그램에 다시 올리지는 않아서
> "(첨부 — 상위 방에 있습니다)" 라고 정직하게 적는다. 완전한 해법은 `copyMessage` 로 원본을
> 토픽에 복사하는 것인데(원본 `message_id` 가 `runRoute` 안에 아직 있다), 보내는 사람이 봇으로
> 바뀌고 실패 경로가 느는 데다 300자 결정과도 어긋나 **열린 질문으로 남긴다.**

### 첨부는 같이 가야 한다 — 여기가 제일 큰 덩어리

지금 `runRelay()` 는 합성 메시지에 `text` 만 담는다. 그런데 **로그 파일이나 스크린샷을 붙여
보내다 방을 틀리는 경우가 오히려 흔하다** — 첨부를 흘리면 이 기능은 절반만 쓸모 있다.

원본 `msg` 를 그대로 들고 있다가 방 키(`chat.id`·`message_thread_id`)만 바꿔 `handle()` 에
넣는 쪽이 맞다. 텍스트만 새로 만드는 것보다 오히려 단순하고, `_mediaGroup` 같은 곁가지도 딸려온다.

### 병합 창 뒤에 한 번만 묻는다

긴 로그를 붙여넣으면 클라이언트가 8조각으로 쪼개 보낸다(`SPLIT_WINDOW_MS`, bot.mjs:167).
조각마다 물으면 버튼이 여덟 번 뜬다. 붙잡는 자리는 병합 창 게이트(bot.mjs:4193) **뒤**,
`drainQueue()` 로 합쳐진 `_drained` 메시지 하나에 대해서만이다.

### 명령은 그대로 통과한다

`/status`·`/stop`·`/tell`·`/router off` 는 접수처에서도 즉시 동작해야 한다. 게이트를 명령
처리가 전부 끝난 자리에 두면 공짜로 지켜진다 — 병합 창이 이미 그 자리에 있다.

### 버튼 순서는 마지막으로 대화한 토픽부터 (0.7.0)

상위 방에 흘리는 말은 대개 **방금까지 일하던 토픽** 얘기다. 그래서 그 토픽을 맨 앞에 놓고, 한 시간
안이면 첫 버튼에만 `· 방금` 을 붙인다. 오래된 방에 붙이면 추천처럼 보여 오히려 잘못 유도한다.

**추측으로 보내는 것과는 다르다** — 순서만 바꾸고 고르는 건 사람이라 틀려도 대가가 없다. 자동 배달
안을 접은 이유(아래 "안 하기로 한 것")가 여기엔 걸리지 않는다. 재시작하면 활동 기록이 없어
(`chatRuntime` 은 메모리다) 예전처럼 제목순이 되는데, 그게 맞다.

### 묻고 고른 것은 로그에 남긴다 (0.7.0)

지금까지 **아무 기록이 없었다.** 몇 번 물었는지, 뭘 골랐는지, 질문이 답 없이 얼마나 묵었는지 알
방법이 없어서 "자동으로 보낼까"를 따질 때 **가정으로 논쟁했다**(2026-10-01). 한 줄씩 남긴다.

```
Router ask: -100… (4 siblings)
Router -100… → -100…:573 (7s)
```

**본문은 안 남긴다.** 빈도·선택·묵은 시간만 알면 되고, 사람 말을 로그 파일로 옮길 이유가 없다.
이게 쌓이면 다음 질문 — 자동 배달이 필요한가 · 창을 늘릴까 · 끈 방이 많나 — 은 `bot.log` 한 번
훑어서 답할 수 있다.

### 목적지 버튼은 같은 그룹의 형제 방만

`knownRooms()` 는 이 봇이 아는 **모든** 방을 준다(다른 그룹·DM 포함). 오배송 교정은 거의 항상
같은 그룹 안이고, 버튼이 열 개로 늘어나면 "탭 한 번"이라는 값이 사라진다. 형제 토픽만 놓고
그 밖으로 보낼 일은 `/tell` 로 남긴다.

### 선택은 메모리에만 둔다

`pendingTells`(bot.mjs:1853) 와 같은 성질이다 — 재시작하면 사라지고, 그 뒤에 누르면 만료
안내가 나간다. 상한도 같이 둔다. 사람이 안 누르고 지나간 말이 디스크에 쌓일 이유가 없다.

## 구현 자리

- 게이트 — 병합 창 게이트 바로 뒤(bot.mjs:4381). ~~`_drained` 메시지에만~~ — **조건에서 뺐다:**
  `_drained` 를 요구하면 병합 창을 끈 방(`/mergewindow off`)에서 게이트가 통째로 안 걸린다.
  자리는 창 뒤 그대로라 "한 번만 묻는다"는 목적은 자리가 지킨다. 대신 `_router`(정한 뒤 되넣은
  말)와 `_relay`(`/tell`·`ctb send` — 이미 사람이 주소를 정한 말)를 건너뛴다. `_router` 가 없으면
  `[여기서 실행]` 이 같은 방으로 되넣으면서 **무한 루프**가 된다
- 방 목록 — `knownRooms()` (bot.mjs:1833) 을 같은 `chat.id` 로 거른다
- 실행 — `runRelay()` (bot.mjs:1873) 를 첨부까지 나르게 고치고, 머리말은 선택제로
- 콜백 접두어 — `tl:` 옆에 `rt:`
- ~~state — `state.sessions[방].router`~~ — ~~**state 를 안 쓴다.**~~ **0.7.0 에서 같은 이름으로
  돌아왔다** — `"off"` 한 값만 저장하고 키가 없으면 켜진 것이다(`planLock` 과 같은 모양이라 끈
  방에만 필드가 생긴다). 정확히 `"off"` 일 때만 끈다: 손편집한 엉뚱한 값은 **묻는 쪽**으로
  실패해야 한다. `/rooms rm` 으로 방을 지우면 같이 사라지고, 슈퍼그룹 승격 때는 세션 버킷이
  통째로 옮겨가므로 따라간다
- 재주소 지정 — 원본 `msg` 를 그대로 들고 `chat.id`·`message_thread_id` 만 바꾼다. **`message_id`
  는 뗀다** — 메시지 ID 는 방마다 별개라, 그대로 두면 목적지에서 엉뚱한 메시지에 👀 를 단다
- 버튼 메시지는 `sendMenu` 가 아니라 `send` — `sendMenu` 로 띄우면 뒤이어 말을 걸 때
  `dropLiveMenu()` 가 버튼을 걷어가고, 붙잡아 둔 말이 손댈 방법 없이 사라진다. 조용히 잃는 것이
  이 기능이 막으려는 바로 그것이다

~~**새 명령이 생기므로 minor 다.**~~ — 명령을 안 만들었으므로 이 사유는 없어졌다. 0.5.0 은
`personas[].dir` 과 `/allow` 로 이미 minor 다.

## 비용

진짜로 상위 방에서 일을 시키고 싶었을 때 탭이 한 번 낀다. `[여기서 실행]` 으로 덜어낸다.
상위 방에서 일을 시키는 빈도가 낮다면 남는 장사이고, 높다면 애초에 `/router on` 을 안 켜면 된다.

## 안 하기로 한 것

- **내용을 보고 방을 추측해 자동 배달** — 모델을 한 번 더 돌려야 하고, 틀리면 실패가 다시
  조용해진다. 지금과 똑같은 사고인데 원인만 하나 늘어난다.
- **텔레그램에서 상위 토픽을 닫거나 숨기기** — 관리자는 계속 쓸 수 있다. 정작 사고를 치는
  사람이 관리자라 막히지 않는다.
- **모든 방에 기본으로 켜기** — DM 과 단일 방 봇에서는 방해일 뿐이다.
- **마지막으로 대화한 토픽으로 자동 배달** (2026-10-01 검토) — 맞는 경우가 하나 있다: 토픽에서
  일하다 상위에 흘린 첫 말은 마지막 토픽이 곧 목적지다. 그런데 틀리는 경우가 더 흔하고 **조용하다**
  — 상위에서 일부러 시작할 때, 사람이 여럿인 방(마지막 토픽은 사람별이 아니다), 재시작 직후
  (활동 시각이 메모리에만 있다), 몇 시간 뒤의 "마지막". 결정적인 건 **방마다 plan 고정·페르소나·
  작업 폴더가 다르다**는 것이다: `plan 🔒` 인 방에 갈 말이 `acceptEdits` 인 방에서 돌면 파일을
  고친다. 탭 하나를 아끼려고 되돌릴 수 없는 쪽을 연다.
- **'방금 고른 방'으로 자동 배달 (2~3분 창)** — "사고는 연달아 난다"를 전제로 한 규칙인데,
  **그 전제에 근거가 없었다.** 관찰이 아니라 가정이었고, 실제로는 잘못 보낸 걸 바로 알아차리고
  그 토픽으로 들어가 이어 말하므로 두 번째가 잘 안 난다. 전제가 빠지면 거의 발동하지 않는다.
  접수처 로그를 쌓아 **반대 증거가 나오면** 그때 다시 꺼낸다.
- **활동 시각을 `state.json` 에 영속화** — 추측 하나 살리자고 스키마를 늘리지 않는다. 재시작하면
  모르는 게 맞다(위 "조용한 창" 참고).
- **단독 '다른 방으로 옮기기' 버튼** — 값이 절반이다. 틀린 방의 Claude 세션은 `r.prevSession` 으로
  되돌릴 여지가 있지만(그 방에서 다음 턴이 안 돌았을 때만), 토큰·파일 변경은 못 되돌리고, 답
  지우기도 `deliver()` 가 **마지막 조각 ID 만** 돌려줘서 긴 답은 반만 지워진다. 자동 배달을 넣는
  날에만 같이 넣는다(그때는 필수다).

## 단계 — **0.5.0 에서 전부 했다**

1. ~~게이트 + 버튼 + 텍스트 이동.~~ **여기까지가 사고를 막는 최소치다.**
2. ~~첨부 동행.~~ — 1 과 한 커밋이 됐다. 원본 `msg` 를 재주소 지정하는 쪽이 텍스트를 새로 만드는
   것보다 오히려 짧아서, 텍스트 전용 판을 먼저 쓰고 지우는 게 순수한 낭비였다.
3. ~~`/router` 명령과 안내 문구~~ — **명령을 안 만들기로 해서 통째로 없어졌다.** `setMyCommands`·
   `helpText` 도 손댈 게 없다. 남은 문서는 README 두 벌의 포럼 절과 CHANGELOG 다.
4. **(0.7.0) `/router on|off` 와 안내 문구** — 예고한 "끄는 용도"로 되살아났다. 여섯 자리를 다
   고쳤다: `helpText`(영·한) · `setMyCommands`(영·한) · README 두 벌. 더해서 `/status` 는 꺼진
   방에만 한 줄, 그리고 접수처 질문 키보드에 `🔕 이 방에선 그만 묻기` 버튼 — 끄는 길을 알 수 있는
   자리가 거기뿐이라 안내 문구 대신 버튼으로 줬다(성가심을 느끼는 바로 그 자리에 있다).
   **그 버튼은 `handledKeyboards` 예외가 필요하다**: 예외가 없으면 누르는 순간 같은 키보드의
   목적지 버튼까지 걷혀서 붙잡아 둔 말이 손댈 방법 없이 사라진다 — 이 기능이 막으려는 바로 그
   "조용히 잃기"를 이 기능이 만드는 꼴이 된다.

  있지만, 그때도 **누른다는 행위 자체가 의식적이라** 조용히 실행되는 것과는 다르다.

  일어난 뒤라 값이 절반이다.
