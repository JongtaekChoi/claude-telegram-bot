# 방 사이 메시지 전달 (`/tell`) — 설계

## 배경

한 봇 프로세스가 여러 방(DM·그룹·포럼 토픽)을 담당하고, 0.4.3 부터 **방마다 세션이 독립**이다
([group-chat-multi-user.md](group-chat-multi-user.md)). 맥락이 갈린 건 의도지만, 그 대가로 한 방에서
알아낸 걸 옆방에 넘길 통로가 없다. 사람이 손으로 복사해 붙여넣는 게 유일한 방법이었다.

여기엔 **같은 봇 안에서 방 사이에 메시지를 넘기는 것**만 다룬다. 서로 다른 봇 프로세스
(개발자 봇 ↔ 기획자 봇) 사이는 별개 문제이고 아래 "다음 단계"에 적었다.

### 텔레그램 쪽 제약 (이게 설계를 가른다)

> **봇은 다른 봇이 보낸 메시지를 받지 못한다.** Bot API 규칙이라 우회가 없다.

같은 그룹에 두 봇을 넣어도 서로의 말을 못 듣는다. 그래서 "봇끼리 대화"는 텔레그램 위에서는
불가능하고, **같은 프로세스 안(이 문서)** 이거나 **파일을 통해서**(다음 단계)만 된다.

## 결정

### 사람이 부르는 길과 에이전트가 부르는 길을 나눈다

- `/tell <방> <메시지>` — 사람이 친다. 대상 방에서 **바로 실행**한다. 이미 사람이 승인한 셈이다.
- `[[ctb-tell: 방 | 메시지]]` — 에이전트가 답변 끝에 남기는 마커(`[[ctb-image:]]` 와 같은 방식).
  대상 방에 **✅/❌ 버튼과 함께 물어보고**, 승인해야 실행한다.

에이전트 쪽만 승인을 거는 이유는 그 자리가 **모델이 스스로 다른 방의 토큰을 쓰기 시작하는 자리**라서다.
사람이 친 `/tell` 은 사람이 이미 그 결정을 했다.

### 답은 되돌아오지 않는다

대상 방에서 나온 답은 그 방에 남는다. 보낸 방으로 자동으로 물어오지 않는다. 되돌리는 순간
A → B → A 가 되고, 그게 핑퐁의 시작이다. 사람은 어차피 두 방을 다 볼 수 있다.

### 되전달 금지 — 홉은 1 이다

전달받아 실행된 턴의 답변에 들어 있는 `[[ctb-tell:]]` 마커는 **버린다.** 마커를 지웠다고 조용히
넘어가지 않고 그 방에 왜 안 갔는지 한 줄 남긴다.

승인과 이 규칙 둘을 합치면 사람 없이 도는 경로가 없다.

```
사람 /tell ──▶ B 방 실행 ──▶ (B 의 답에 마커가 있어도) 버림
에이전트 마커 ──▶ B 방에 물음 ──▶ 사람이 ✅ ──▶ B 방 실행 ──▶ 버림
```

### 아는 방만 대상이 된다

`state.sessions[방].title` 이 있고 `allowedChatId` 안에 있는 방만 목록에 오른다. 이름은 그 방에
메시지가 한 번 오갔을 때 적힌다 — 봇이 먼저 말을 걸 수 있는 방을 "이미 대화한 적 있는 방"으로
제한하는 효과가 있다.

방 지정은 **번호**(`/tell` 목록 순서)나 **이름의 일부**로 한다. 포럼 토픽 이름은
`큐브기획방 / 마케팅` 처럼 공백이 들어가서 전체를 치게 하면 못 쓴다. 여러 방이 걸리면 후보를
보여주고 멈춘다.

### 받는 방의 실행 규칙은 그대로 따른다

전달된 프롬프트는 대상 방의 큐·`busy` 락·provider·model·plan 고정을 **그 방 것**으로 따른다.
보내는 방의 설정은 하나도 넘어가지 않는다. 대상이 바쁘면 그 방 대기열에 쌓인다 — 이미 되는 동작이다.

`/*` 로 뮤트된 방에는 보내지 않고 보낸 쪽에 알린다. 뮤트는 "지금 이 방은 아무것도 실행하지 마라"는
뜻이라 전달도 예외가 아니다.

### 전달된 프롬프트는 출처를 밝힌다

```
[Relayed from: 큐브기획방 / 마케팅 — another room of this bot]
```

이 태그가 없으면 받는 세션은 사용자가 한 말로 착각한다. `buildMsgMeta()` 의 `[From: …]` 과 같은
형식을 쓴다 — 에이전트가 이미 아는 모양이다. 태그가 맨 앞이라 본문이 `/` 로 시작해도 명령으로
해석되지 않는다(부수 효과지만 의도한 것이다).

## 구현 메모

- 전달은 대상 방 키로 **합성 메시지**를 만들어 `handle()` 에 넣는 것이다. 큐·락·병합·레이트리밋
  경로를 다시 짜지 않고 그대로 탄다. `_drained` 를 찍어 병합 창에는 붙잡히지 않게 한다.
- 병합(`drainQueue`)에서 전달 메시지가 섞이면 합쳐진 턴 전체를 전달받은 것으로 본다(`_relay`).
  하나라도 전달이면 되전달을 막는 쪽이 안전하다 — `_approvedPlan` 과 같은 판단이다.
- 승인 대기(`pendingTells`)는 메모리에만 둔다. 재시작하면 사라지고, 눌러도 만료 안내가 나간다.
  계획 승인(`pendingPlans`)과 같은 성질이다.
- 시스템 프롬프트의 사용법 안내는 **넘길 방이 실제로 있을 때만** 붙인다. 방이 하나뿐인 봇은
  토큰을 내지 않는다.
- `"roomRelay": false` 로 기능 전체를 끈다 (`sendImages`·`backgroundJobs` 와 같은 자리).

## 안 하기로 한 것

- **답 되돌리기(에코).** 위 참조. 필요하면 사람이 `/tell` 로 다시 넘기면 된다.
- **다른 봇 프로세스로 보내기.** 같은 명령으로 되게 하려면 파일 인박스가 필요하다 — 다음 단계.
- **봇이 먼저 말 거는 방 추가.** 아직 대화한 적 없는 방으로는 보낼 수 없다.

## 다음 단계 — 봇 사이 전달 (미구현)

다른 봇은 프로세스도 토큰도 `projectDir` 도 다르다. 텔레그램으로는 못 닿으니 파일이 유일한 통로다.

```
보내는 봇 → <상대 projectDir>/.claude-bot/inbox/<uuid>.json → 받는 봇이 주워서 자기 방에 물어봄
```

여기서 정한 규칙(승인, 홉 1, 출처 표기, 아는 방만)은 그대로 쓴다. 추가로 정해야 할 것:

- 상대 봇의 `projectDir` 을 어디서 아는가 (config 에 이름 → 경로 표를 두는 쪽이 유력)
- 인박스를 언제 읽는가 (`.ctb-jobs` 처럼 30초 감시)
- 어느 방에 물어보는가 (받는 봇의 주 방, 보통 `allowedChatId[0]`)
- 상대 봇이 떠 있지 않을 때 쌓인 파일의 수명
