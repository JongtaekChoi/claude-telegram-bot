# 그룹 채팅 다중 사용자 처리 — 기획

## 배경

그룹 채팅에서 여러 명이 같은 봇에 메시지를 보낼 때 두 가지 의문이 제기됨:

1. 봇이 메시지를 보낸 사람을 구분해서 인식하는가?
2. 봇 프로세스(config 파일 하나)가 여러 채팅방에 걸려 있을 때, 방마다 별도 세션을 유지하는가?

코드 확인 결과 둘 다 "아니오":

- `buildMsgMeta()`(bot.mjs:1228)는 포워드(`forward_origin`/`forward_from`)와 리플라이(`reply_to_message`)에 한해서만
  발신자 이름을 컨텍스트에 넣는다. **지금 보낸 메시지 자체**에는 발신자 태그가 없다 — Claude 입장에서는
  그룹방의 여러 사람이 한 명처럼 보인다.
- `state`(bot.mjs:525)는 봇 프로세스당 전역 객체 하나이고 `state.sessionId`/`state.codexSessionId`는
  어디서도 `chatId`로 키잉되지 않는다. `allowedChatId`가 배열이어도(bot.mjs:124) 그 방들은 세션 하나를 공유한다.

이건 버그가 아니라 `docs/ROADMAP.md` 3번("그룹 채팅 지원") 항목에 이미 명시된 설계 의도다:
> 세션은 그룹 전체가 공유 (팀이 같은 프로젝트 보는 용도)

즉 "그룹 = 한 프로젝트를 같이 보는 팀, 세션 공유가 기본"이라는 전제가 깔려 있다. 이 문서는 그 전제를
유지한 채로 "누가 말했는지"만 보이게 하는 **1단계(발신자 표시)** 와, 그 전제 자체를 재검토하는
**2단계(방별 세션 분리)** 를 분리해서 정리한다.

## 1단계 — 발신자 표시 (지금 구현)

### 목표
그룹 채팅(`msg.chat.type`이 `group`/`supergroup`)에서 온 메시지에 발신자 이름을 붙여 Claude가
"누가 말했는지"를 알 수 있게 한다. 1:1 채팅(`private`)은 어차피 사람이 한 명이므로 건드리지 않는다
(프롬프트에 불필요한 노이즈를 추가하지 않기 위함).

### 대상 코드 두 곳

1. **`buildMsgMeta(msg)`** (bot.mjs:1228) — 단일 메시지 처리 경로. 그룹 채팅이면 현재 메시지의 발신자를
   `[From: {first_name}{ (@username)}]` 형태로 맨 위에 추가.
2. **`drainQueue()`** (bot.mjs:1815) — `busy` 중 쌓인 메시지를 하나로 합치는 경로. 지금은
   `...group[group.length - 1].msg`로 **마지막 메시지의 `from`만** 합성 메시지에 남기고, 각 줄(`[1] text`,
   `[2, +Ns] text`)에는 발신자 정보가 없다. 그룹방에서 여러 사람이 큐잉된 상태로 섞여 들어오면 전부
   마지막 사람이 말한 것처럼 보이는 별도 버그이기도 함 — 같이 고친다. 줄마다
   `[1] Alice: text` / `[2, +Ns] Bob: text` 형태로 발신자를 표기.

### 표시 형식
- `[From: Alice]` — username 없으면 first_name만.
- `[From: Alice (@alice_tg)]` — username 있으면 병기.
- 봇 자신에게 보낸 리플라이/포워드 태그와 형식을 맞춰 Claude가 이미 익숙한 패턴을 재사용한다.

### 비범위
- 세션 분리는 하지 않는다 (2단계).
- 사용자별 권한/화이트리스트는 다루지 않는다 — 그룹방에 있는 사람은 이미 `allowedChatId`를 통과한
  것으로 간주 (텔레그램 특성상 봇은 그룹 멤버 개개인을 승인할 수 없고 방 단위로만 승인 가능).

## 2단계 — 방별 세션 분리 (추후, 미착수)

### 문제 의식
`allowedChatId` 배열에 서로 다른 프로젝트/목적의 방(예: 개인 DM + 별도 그룹)이 섞여 있으면 세션 공유가
오히려 컨텍스트 오염을 일으킨다. ROADMAP 3번의 "팀이 같은 프로젝트를 보는 용도"에는 세션 공유가 맞지만,
그 가정이 깨지는 배치(같은 config로 서로 무관한 방을 여러 개 허용)에서는 안 맞는다.

### 변경 범위 (설계만, 아직 구현 안 함)
- `state.sessionId` / `state.codexSessionId` → `state.sessions[chatId]` 형태의 맵으로 변경.
- `state.json` 스키마 마이그레이션 필요: 기존 단일 `sessionId`를 첫 실행 시 어느 chatId에 매핑할지
  결정해야 함 (예: `allowedChatId`가 하나뿐이면 그대로 이전, 여럿이면 사용자에게 선택하게 하거나
  전부에 복사).
- `state.sessionId`를 읽고 쓰는 모든 호출부(`replyWithClaudeResult`, `/new`, `/stop`, `/compact`,
  `/status`, cron 핸들러 등 10곳 이상, bot.mjs 전역)를 `chatId` 인자를 받도록 수정.
- cron 작업(`handleCron`)과 스케줄러는 애초에 특정 채팅에 묶여 있지 않고 `allowedIds` 전체로 브로드캐스트
  하는 구조(bot.mjs:1079)라 "방별 세션" 개념과 충돌 — 스케줄 작업이 어느 세션에 붙을지 별도 결정 필요.
- `/plan` 승인 대기(`pendingPlans`)는 이미 `chatId` 키 맵(bot.mjs:1274)이라 참고할 선례가 됨.

### 열린 질문
- ROADMAP 3번의 "그룹 = 공유 세션" 전제를 유지하면서 "서로 다른 방은 분리"만 원하는 것인지, 아니면
  그룹 안에서도 사람별로 분리하고 싶은 것인지 — 후자는 텔레그램 그룹 특성상 사실상 개인 DM처럼 쓰라는
  뜻이라 봇 설계 철학(방 하나 = 컨텍스트 하나)과 충돌할 수 있음. **사람별 세션 분리는 이 문서의 범위 밖으로
  명시적으로 제외** — 필요해지면 별도 문서로 다룬다.
- 마이그레이션 시 기존 사용자의 진행 중인 세션을 깨지 않는 방법 확정 필요.

### 권장
1단계(발신자 표시)만으로도 "누가 무슨 말을 했는지 구분이 안 된다"는 원래 불편함의 상당 부분은 해소된다.
2단계는 실제로 한 config에 서로 무관한 방을 여러 개 등록해서 쓰는 경우가 생기면 그때 착수하는 쪽을
권장 — 지금은 설계만 남겨두고 보류.
