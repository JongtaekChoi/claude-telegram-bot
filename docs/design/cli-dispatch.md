# CLI 에서 봇에 일 시키기 (`ctb send`) — 설계

## 배경

지금 `ctb` 는 **자기가 `claude` 를 띄운다.** 봇은 그 일을 모른다. 방에는 typing 도 안 뜨고, 답도
터미널에만 남고, 봇의 큐·락과도 무관하다. 세션이 끝날 때 인수인계 한 줄을 보내는 게 접점의 전부다.

원하는 건 반대다. **CLI 가 프롬프트를 돌고 있는 봇에 넘기고, 봇이 그 방에서 처리한다.** 방에는
"메시지를 받아 처리 중"이라고 뜨고 typing 이 돌고, 답이 그 방에 남는다 — 사람이 텔레그램으로 보낸
것과 **구별되지 않는 상태**가 목표다.

동기는 `ctb` 를 사람이 치는 그림이 아니라 **에이전트가 부르는 그림**이다. 로컬 터미널에서 도는
Claude 가 옆방(다른 역할)에 일을 넘길 수 있게 된다 — `/tell` 이 방 사이에 하는 일을,
프로세스 밖에서 하는 셈이다.

## 봇 안쪽은 이미 다 있다

`/tell` 이 정확히 이 일을 한다 — 대상 방 키로 **합성 메시지**를 만들어 `handle()` 에 넣으면
typing·`busy` 락·큐·병합 창·레이트리밋·plan 고정·답 전송이 전부 따라온다
(`runRelay`, [room-relay.md](room-relay.md)). `runScheduled` 도 같은 모양이다.

**없는 건 프로세스 경계 하나뿐이다: `ctb` → 봇.**

## 결정

### 통로는 유닉스 소켓

의존성 0 을 지키면서 뚫는 길은 둘이다.

| | 파일 인박스 | 유닉스 소켓 |
|---|---|---|
| 선례 | `local.lock` · `.ctb-jobs` | 없음 (`net` 은 이미 import 돼 있다) |
| 지연 | `fs.watch` 면 즉시, 폴링이면 최대 30초 | 즉시 |
| 답을 stdout 으로 | **못 준다** | 준다 |

**소켓으로 간다.** `-p` 로 부르는 쪽은 답을 파이프로 받으려는 것이고, 파일 인박스엔 돌아오는 길이
없다. 답은 방에도 뜨고 stdout 으로도 온다. 소켓 파일은 `.claude-bot/ctb.sock`, 즉 config 폴더
아래라 봇마다 자연히 갈린다(`state.json` 과 같은 규칙).

봇이 안 떠 있으면(소켓 없음·연결 거부) **그 자리에서 실패한다.** 예전 방식(ctb 가 직접 claude
실행)으로 조용히 물러서면 typing 도 방 안내도 없이 돌아서, 원한 것과 정반대인데 성공한 것처럼
보인다.

### 새 명령으로 뺀다 — `-p` 를 재활용하지 않는다

설계 초안은 `ctb --chat <방> -p "…"` 였다. **뒤집었다.** `-p` 는 지금 이미 "로컬에서 헤드리스로
돌린다"는 뜻이고, 같은 명령줄이 갑자기 다른 일(봇에 넘기기)을 하면 기존 스크립트가 조용히 다른
동작을 한다. `ctb send` 라는 별도 명령으로 뺀다.

```
ctb send [config.json] --chat <방> [--now] <메시지>
```

`--chat` 은 방 키 그대로도, **이름의 일부**로도 받는다(`--chat 마케팅`). 봇의 `/tell` 이 같은
이유로 그렇게 한다 — 포럼 토픽 이름엔 공백이 들어가서 전체를 치게 하면 못 쓴다. 방을 아예 안 주면
**아는 방이 하나뿐일 때만** 그걸 쓰고, 여럿이면 목록을 보여주고 멈춘다. 스크립트가 엉뚱한 방으로
가는 것보다 멈추는 쪽이 낫다.

### 주소는 방이다

typing·큐·"메시지 받았습니다" 안내는 전부 **방**에 붙는다. 세션은 방이 들고 있는 것이다.
그래서 `--chat <방키>` 로 주소를 잡는다 — 이미 있는 옵션이고, `ctb` 가 방을 고를 때 손에 쥐는 값이다.

`--session <id>` 는 **안 만든다.** 부르는 쪽(에이전트)이 손에 쥔 건 방이지 세션 ID 가 아니고,
어느 방도 안 쥔 세션을 지목하면 narration 할 방이 없어진다.

### 기본은 대상 방의 승인을 받는다

`/tell` 에서 **에이전트 마커만** 대상 방 승인을 받게 한 이유가 그대로 여기 적용된다 —
"모델이 스스로 다른 방의 토큰을 쓰기 시작하는 자리"([room-relay.md](room-relay.md)).
CLI 를 그냥 열어주면 그 구멍이 옆문으로 다시 열린다.

게다가 **프로세스는 사람이 친 `ctb` 와 에이전트가 부른 `ctb` 를 구분할 방법이 없다.** 구분이
불가능하면 안전한 쪽을 기본으로 둬야 한다.

- 기본 — 대상 방에 본문과 ✅/❌ 를 띄우고, 승인해야 실행한다. 어차피 답을 보러 그 방에 가 있다.
- `--now` — 무인 스크립트·cron 용 명시적 우회. **사람이 그 명령줄을 직접 썼다는 뜻**이다.

### 자기가 쥔 방으로는 못 보낸다

`ctb` 는 자기가 잡은 방에 `local.lock` 을 걸고, 봇은 잠긴 방의 실행을 미룬다. 그 방에 밀어 넣으면
**터미널 세션이 끝날 때까지 큐에서 안 나온다.** 조용히 멈추는 대신 그 자리에서 거절한다.

옆방으로 보내는 건 막을 이유가 없다 — 그게 이 기능의 본래 쓰임이다.

### 밀어 넣은 프롬프트는 다시 전달 못 한다

합성 메시지에 `/tell` 의 홉 1 표시(`_relay`)를 그대로 붙인다. 안 그러면
**CLI → 방 A → 마커 → 방 B** 로 사람 없이 도는 길이 생긴다. 승인과 합치면 고리가 없다.

### 출처를 밝힌다

방에 뜨는 안내와 세션에 들어가는 프롬프트 모두 **터미널에서 왔다**고 적는다. 없으면 받는 세션은
사용자가 방에서 한 말로 착각하고, 방을 보는 사람은 자기가 안 친 메시지가 처리되는 걸 본다.
`ctb` 종료 알림이 이미 쓰는 `💻 [터미널]` 표식과 같은 계열로 간다.

## 안 하기로 한 것

- **`--session <id>`** — 위 참조.
- **봇이 없을 때 예전 방식으로 폴백** — 위 참조.
- **답을 기다리지 않고 바로 빠지는 모드** — 필요해지면 그때. 기본은 답까지 기다린다(스크립트가
  이어서 뭔가 하려면 답이 있어야 한다). 대상 방이 바빠 큐에 쌓이면 그만큼 기다린다.

## 정한 것 (구현 시점)

- **프로토콜 — 줄 단위 JSON.** 요청 한 줄(`{room, text, now}`), 응답은 여러 줄일 수 있는데
  **`ok` 가 들어 있는 줄이 마지막**이다. 중간 줄은 진행 상황(`{status: "running"}` ·
  `{status: "awaiting-approval"}`)이고 `ctb` 는 그걸 stderr 로, 결과만 stdout 으로 낸다 —
  파이프로 답만 받아 쓸 수 있게.
- **타임아웃은 봇 쪽 한 곳에.** 승인 대기 10분(`PENDING_DISPATCH_TTL`)이 끝이고, 만료되면 방과
  터미널 양쪽에 알린다. 클라이언트에 별도 시계를 두지 않는다 — 시계가 둘이면 어긋난다. 실행 자체의
  상한은 봇이 원래 쓰던 것을 그대로 따른다.
- **승인 대기 중 `ctb` 는 기다린다.** 답을 받는 게 목적이고, 위 10분 만료가 무한 대기를 막는다.
- **소켓 권한 0600**, 봇 폴더 안. 봇마다 자연히 갈린다.
- **`--now` 남용은 막을 수 없다 — 대신 보이게 한다.** 프로세스는 사람이 친 `ctb` 와 에이전트가
  부른 `ctb` 를 구분하지 못하므로 기술적 차단이 성립하지 않는다. 우회할 때마다 대상 방에
  "터미널에서 온 요청"이라고 띄워서 사람이 **매번 보게** 한다. 그리고 로컬 셸을 쥔 쪽은 이미
  `config.json` 도 고치고 `claude` 도 직접 돌릴 수 있으니 **신뢰 경계 안**이다 — 여기서 막아도
  옆으로 돌아간다.

## 매달리지 않는 게 제일 중요하다

승인 뒤로는 클라이언트에 시계가 없다("큐가 빌 때까지 기다린다"는 결정의 대가다). 그래서 **답이 한 번
안 가면 터미널은 영영 매달린다.** `handle()` 의 출구는 여럿이고(폴백 성공, `/stop`, 뮤트, 예외,
로컬 락) 부르는 자리마다 챙기면 반드시 빠뜨린다 — 실제로 적대적 검토에서 일곱 군데가 나왔다.

그래서 콜백을 메시지에 직접 달지 않고 **토큰**을 달고, 정산은 세 자리에서만 한다.

1. **답이 나갈 때** — `replyWithClaudeResult` 의 성공·실패, 그리고 **Codex·Ollama 폴백 성공.**
   폴백은 무인 실행에서 가장 잘 걸리는 경로인데 답을 방에만 보내고 있었다.
2. **`handle()` 이 끝났는데 답이 없을 때** — `runDispatch` 가 `await handle()` 뒤에 확인한다.
   단, **큐에 남아 있으면 아직 차례가 안 온 것**이라 건드리지 않는다. 이 한 자리가 handle 의 모든
   조기 반환을 덮는다.
3. **큐를 버릴 때** — `/stop` · `/restart` 는 대기 메시지를 통째로 지운다. 지우기 전에 그 안에 든
   요청을 정산한다.

병합(`drainQueue`)에서는 토큰을 **전부** 넘긴다. 하나만 챙기면 같이 합쳐진 다른 터미널이 매달린다
— `_relay` 는 하나만 봐도 되지만(표시일 뿐이라) 여기는 아니다.

뮤트된 방은 아예 **입구에서 거절**한다(`/tell` 과 같은 규칙). 안 그러면 `handle()` 이 조용히 삼킨다.

## 알아둘 것

- **plan 이 고정된 방에 보내면 돌아오는 건 "계획"이다.** 승인 후 실행 결과는 `runApprovedPlan` 이
  새 합성 메시지로 돌리므로 터미널에 닿지 않는다. 스크립트가 그걸 결과로 알고 쓰면 안 된다.
- **로컬 락은 입구에서 한 번만 본다.** 승인 대기 10분 사이나 큐에 있는 동안 그 방을 `ctb` 세션이
  잡으면 봇이 메시지를 흘린다 — 그때는 위 2번이 "답 없이 버려졌다"고 알려 준다.

## 남은 것

- **`ctb send` 는 답을 끝까지 기다린다.** 대상 방이 바쁘면 그 방 큐가 빌 때까지 매달린다. 오래
  걸리는 방에 던져 놓고 빠지는 모드(`--detach` 류)는 필요해지면 그때 연다.
